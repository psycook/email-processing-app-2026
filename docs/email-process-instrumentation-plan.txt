Four independently approvable stages

DECISION SUMMARY

1. Replace the six-box illustration with a read-only, BPMN-inspired process
   canvas: swimlanes, task nodes, gateways, explicit outcomes and drill-down.
2. Use standard Dataverse tables for versioned process definitions, actual
   message instances, stage executions, immutable events and case links.
3. Build a C# Dataverse plug-in behind narrow Custom API Actions. All producers
   use one validated writer; the app and flows can query through the same
   service boundary. Observe committed case lifecycle changes independently.
4. Optionally add a durable outbox, Azure Service Bus and Web PubSub. Push
   accelerates the display; it does not replace the ledger or reconciliation.

This supersedes the 1 October two-table proposal. In particular, it withdraws
the old recommendation to append GB-STUDIO IDs to email subjects. Subjects and
bodies remain natural; Reply-To remains explicitly demo customer-routing data.
More tables are justified here by the new requirement to persist the process
graph, stage executions and many-to-many case relationships independently.

STAGE 1 - PROFESSIONAL PROCESS EXPERIENCE
Approval scope: front-end design and implementation only.
Dependencies: none beyond the current app.

1.1 Visual design

Use a BPMN-inspired view, not a claim of executable BPMN conformance and not a
replacement for the actual Power Automate orchestration.

- Swimlanes: Email channel, Workflow orchestration, Agents/tools, Case handling.
- A message-start event; compact task/subprocess shapes; decision diamonds with
  labelled branches; orthogonal connectors; explicit completion and exception
  endpoints. Show human review as a branch/waiting loop, not a mandatory last
  step after every automated action.
- Preserve the recognisable business phases: intake, identify, classify, route,
  act and review. Map each actual operation to a phase without inventing a
  fixed order. In the current definition classification precedes the handler;
  identification may occur inside that handler.
- Collapsible agent/tool subprocesses. If only an outer invocation is observed,
  show that one span and an explicit "internal steps not instrumented" label.
- One reusable process renderer: compact Overview view plus full Process Studio
  with fit-to-view, zoom, lane labels, selection and a detail drawer.
- Retain Gravity branding, light/dark themes and restrained motion. Animate
  only observed transitions/running work. Respect reduced-motion preferences.
- Read-only graph: no drag-to-reorder stages, execute buttons or flow editor.

Recommended implementation: bundled @xyflow/react with custom node/edge
components and a deterministic layout for the initial graph. Do not add a full
BPMN execution engine or automatic-layout service. If the component spike shows
accessibility or layout problems, a controlled SVG renderer is the fallback.
Dependency/license review and a published-player smoke test belong to Stage 1.

1.2 Meaningful views, not decorative status

- Definition view: what the deployed process is configured to do.
- Instance view: one received message and the events/stage executions actually
  observed for it. Drill down to native workflow run, agent conversation,
  Contact, holding, case, task or note when a valid reference is available.
- Overview metrics: clearly scoped to the same received-message cohort and
  coverage version. Open-case backlog remains a separate current-state metric.
  Never display Inbox sample count and open-case count as a conversion funnel.
- Node states distinguish not started, running, waiting, succeeded, failed,
  skipped, cancelled and unknown/uninstrumented. Absent telemetry is not success.
- Details show observed time, duration provenance, attempt, source and freshness.
  Recorded time and occurred time are distinct; waiting time is not handling.
- Provide a keyboard-accessible ordered/list alternative, descriptive status
  text and icon/shape cues in addition to colour. Mobile uses a legible vertical
  view rather than squeezing an entire graph into tiny horizontal nodes.

1.3 Integration seams and acceptance

Define typed ProcessDefinition, ProcessSnapshot, StageExecution and ProcessEvent
DTOs before building the canvas. Stage 1 uses fixtures with the Stage 2 contract;
until real producers are connected, retain explicit config-only/synthetic labels.

Deliverables:
- Updated Overview and Process Studio renderer/details/list view.
- Fixture scenarios: straight-through, human handoff, parallel branches, failure,
  retry, skipped stage, reopened case, unavailable source and unknown coverage.
- No new Dataverse tables, live telemetry claims, flow edits or Azure dependency.

Acceptance:
- User approves desktop/mobile, light/dark and one-message walkthrough.
- The graph depicts the inventoried execution, not the old assumed sequence.
- Keyboard access, reduced motion, long labels and empty/error states work.
- Poll refresh does not lose selection, restart animation or move the diagram.
- Same underlying record set/cohort yields consistent counts across views.

Rollback: a UI feature flag restores the existing renderer without changing
data, connectors or workflow behaviour.


STAGE 2 - DATAVERSE SCHEMA, KEYS AND PRODUCER CONTRACT
Approval scope: schema, definition seed data, security design and wiring map.
Dependencies: agreed semantics from Stage 1; live writers wait for Stage 3.

2.1 Recommended standard tables

Use standard, not elastic, tables because the event/projection writes need
Dataverse transaction support. These are custom tracking tables, not Dynamics
Business Process Flow processstage records. A BPF ribbon can be added later but
is not a substitute for concurrent, retryable, message-level execution tracking.

CONFIGURATION - organisation-owned, versioned and read-only after publication:

A. rfd_processdefinition
   Key: primary GUID; unique (DefinitionCode, Version).
   Fields: code, name, version, draft/published/retired state, coverage version.
   Purpose: a stable version of the observed business graph and completion rules.

B. rfd_processstagedefinition
   Key: primary GUID; unique (ProcessDefinition, StageCode).
   Fields: definition lookup, stable stage code, business phase, label, lane,
   node kind, display order, required/optional policy, instrumentation coverage.
   Purpose: graphical stage/node metadata. Coverage is explicit, not inferred.

C. rfd_processtransition
   Key: primary GUID; unique (ProcessDefinition, TransitionCode).
   Fields: definition, from-stage/to-stage lookups, label, branch/event code,
   display order and required/optional branch metadata.
   Purpose: edges for the read-only graph and allowed observed transitions.
   Conditions are allowlisted codes/metadata, not arbitrary stored executable code.

RUNTIME - user/team-owned, with explicit reader/producer/administrator roles:

D. rfd_emailprocess
   Key: primary GUID is the canonical ProcessId, also called TraceId.
   Alternate key: IngestKey, a server-computed 64-character SHA-256 hex string.
   Fields: definition/version lookup, lifecycle state, received time, latest
   event time, projection revision, coverage/health, parent process, optional
   full BatchId and registered DraftId, weak-correlation flag/reason.
   Restricted fields: raw InternetMessageId, mailbox source locator, actual From,
   received Reply-To, selected/effective customer email and identity-source code.
   References: optional Contact and Dataverse email activity lookups; a primary
   case is only a convenience reference, never the full relationship model.

E. rfd_emailprocessstage
   Key: primary StageExecutionId GUID, reused as SpanId.
   Alternate key: SourceOperationKey (server-computed hash) where source identity
   is stable. It includes process, producer/run, operation, branch/iteration
   scope and genuine attempt number; it must never be an empty placeholder.
   Fields: Process and StageDefinition lookups, optional parent execution,
   branch/scope, attempt number, state, start/end times, measured duration,
   duration provenance, native run/conversation reference, optional workflow
   definition and Case lookup, last applied source version.
   One row per actual stage/agent/tool execution attempt. A retry gets a new row;
   a repeated notification about that attempt updates the same row.
   The UI groups attempts under their logical stage; parallel branches remain
   independently visible. Unstarted/unknown graph nodes derive from the
   definition's coverage, not fabricated execution rows.

F. rfd_emailprocessevent
   Key: EventId primary GUID, allocated once before a producer retries a write.
   Alternate key: SourceEventKey, a non-null server-computed scoped digest.
   Fields: process/stage-execution references, event type, stage/outcome codes,
   source execution/version, occurred UTC, recorded UTC, projection revision,
   schema version, payload digest, authenticated producer/initiating actor,
   sanitized error code and explicitly reported duration/usage.
   Optional typed lookups: Case, Contact, financial holding, task, note and
   Dataverse email. Native cloud run/conversation IDs are external references,
   not fake Dataverse lookups. Use an allowlisted link builder for external URLs.
   Append-only event facts; no email body, subject, prompts, reasoning,
   attachments, full account/card numbers or arbitrary error payloads.

G. rfd_emailprocesscase
   Key: primary GUID; unique (EmailProcess, Case).
   Fields: typed process/case lookups, relationship role, blocks-completion flag,
   linked time, source event, last observed case state/status/version.
   Purpose: many messages can relate to one case, and one message can create
   several cases. Case changes can find all explicitly linked processes.
   Other typed event links preserve provenance to tools' actual CRM writes.

No extra per-customer telemetry table, data warehouse or token-cost dimension
is needed. Stage 4 adds one optional notification-outbox table, not another
business source of truth.

2.2 Correlation decision

CANONICAL KEY: full GUID ProcessId/TraceId, created at first Help intake.

INGESTION IDENTITY:
  IngestKey = SHA-256(length-prefixed UTF-8 components:
      "v1", DataverseOrganisationId, serverConfiguredLogicalMailboxKey,
      InternetMessageId.trim())

- Preserve the InternetMessageId's case and brackets; do not silently truncate
  it. Store the original in restricted text metadata, not in a key-addressed URL.
- Dataverse alternate-key URLs reject some characters common in raw message IDs;
  the fixed hex digest avoids those character and collation problems.
- Hashing happens in one server implementation, not invented flow expressions.
- Await Active alternate-key indexes and validate non-null key values server-side;
  required UI fields alone are not a server integrity guarantee.
- Duplicate deliveries of the same source email resolve to the same process.
  Distinct processing attempts retain their own stage executions/events.
- Replies and forwards are distinct messages/processes. Link parent messages
  using transport references where available; conversationId only groups them.
- Graph/Outlook message.id is a locator, not the canonical identity. Store an
  immutable Graph locator if supported by the chosen read path; do not assume
  the current connector ID survives folder moves.
- Customer email, Reply-To, subject, case number, flow definition ID and agent
  conversation ID are NOT process keys.
- A reused InternetMessageId with conflicting reliable source identity is a
  correlation anomaly, not permission to overwrite an existing trace.
- If InternetMessageId is absent, first try a supported detailed message read.
  If still absent, record weak/pending correlation with source execution and
  available locator. Never hash an empty ID or promise replay deduplication for
  an unstable locator. Route ambiguous association for reconciliation.

STUDIO PRE-SEND CORRELATION - EXPLICIT LIMIT:

SendEmailV2 returns no message ID and new subjects have no marker. Therefore:
- Default scope is reliable tracing from Help receipt onwards.
- Keep pre-send DraftId and a new full BatchId separate from ProcessId until
  transport evidence establishes the association. Existing single-/batch-
  eight-character labels are not canonical GUID keys.
- Existing subject/time/Reply-To matching remains candidate-only. Two similar
  emails from the same customer must not silently merge into one trace.
- Do not reintroduce subject tags, BCC or invisible body markers.
- If exact draft-to-intake tracing is required, approve a bounded transport
  spike in Stage 3: prove a supported draft/send operation can retain a custom
  X-Gravity-TraceId header or return a usable transport identity, and that Help
  can retrieve it. The current SendEmailV2 contract does not expose custom
  headers. No implementation is promised until the connector/auth/attachment/
  unknown-send behaviour is proven. Otherwise keep the honest ingress-first
  boundary; this does not weaken downstream process/case tracking.

CUSTOMER IDENTITY IS SEPARATE:
Preserve actual From, Reply-To, resolved Contact and identitySource. Apply the
Reply-To override only in the explicitly approved demo route with a single
eligible Contact and validated internal demo sender/origin. An authenticated
flow connection does not authenticate the sender of every email it processes,
and matching a From string alone is not proof of origin. It is not KYC or
consent to perform servicing/financial actions.

2.3 State and relationships

Process states: received, processing, waiting-review, completed, failed,
cancelled and needs-reconciliation. Telemetry coverage/freshness is separate
from business outcome. "Failed" describes observed failure, not absent events.

Execution states: running, waiting, succeeded, failed, skipped, cancelled.
Unknown/uninstrumented/not-started are also presentation/read-model states;
do not assign completed/skipped to a stage merely because it has no record.

Completion requires all applicable required branches and blocking case links
to satisfy the definition's versioned completion rule. Explicit no-case terminal
routes can complete without a case. Open case counts alone never prove routing
or human review happened. A successful agent message or flow termination alone
does not prove a requested banking action succeeded.

Case resolved, cancelled and merged are different outcomes. On Hold/Waiting
for Details are still active. Reopening creates a new lifecycle event/review
attempt and reevaluates affected blocking links without erasing prior history.

Definition versions are immutable once used. New flow shapes create a new
definition version; existing processes retain their version unless a separately
approved migration explicitly records the remap.

2.4 Producer mapping to approve

- Help trigger: resolve ingestion identity; receive event; carry ProcessId and
  current source-run identity through all subsequent actions.
- Classify_Email: record invocation start/end/failure and validated category;
  do not invent confidence or token usage absent from the actual response.
- Switch: record chosen branch or explicit default/skip, not every branch.
- Agent host: create outer execution span before invocation and settle it from
  the actual result. Saved-agent tools need deterministic wrappers/host context.
  Do not rely on an LLM remembering to call a logging tool or copying IDs.
- Record successful customer lookup, actual case/task/note/holding action and
  linked row IDs at the tool boundary. Unobservable internals stay opaque.
- Case Management Workflow: record its own execution/action outcomes and pass
  case/process references into the shared service; see Stage 3 lifecycle rules.
- Studio: record confirmed operations separately from mere page views. Opening
  a page is not employee handling time. Preserve existing send/review approvals.

2.5 Security, retention and Stage 2 acceptance

Configuration rows are readable to authorized app users, writable to definition
administrators. Runtime rows have a consistent operations-team/user ownership
policy; a linked case does not automatically confer permissions on telemetry.
Restrict sensitive message identifiers and identity fields. Define reader,
producer, reviewer and retention-admin roles; no ordinary event update/delete.
Choose relationship deletion behaviour explicitly: never cascade a case
deletion into silent loss of telemetry history. Coordinate unlink/anonymisation
with retention policy rather than accidentally blocking business deletion.

Proposed starting retention: 90 days of event detail, subject to demo capacity
and privacy approval. Keep open-process summaries/case links until their
closure policy permits removal. Mark truncated histories; retained summaries
cannot promise full replay after underlying event retention expires.
Sizing example: 5,000 messages/month x 20 events = 100,000 event rows/month,
plus stage attempts, process and link rows. Measure actual storage and request
consumption; do not invent a per-event monetary cost.

Acceptance:
- Review an ERD/data dictionary, field lengths/types/choice values, ownership,
  deletion/retention rules, versioning and all alternate keys.
- Demonstrate one message/two cases and two messages/one case with fixture data.
- Duplicate source keys are prevented; null/missing ID policy is explicit.
- Verify record visibility for two different app users and the flow identity.
- Confirm real flow/agent/closure mapping, including uninstrumented boundaries.
- Create schema through supported metadata tools in the approved solution;
  export/unpack generated solution metadata for source control after approval.
- No live producer cutover until Stage 3 owns writes and passes its acceptance.

Rollback: disable feature flags/readers; retain additive tables and data.
Do not delete tables or revert shared business records as an automatic rollback.


STAGE 3 - PLUG-IN-BACKED PROCESS SERVICE AND LIVE INSTRUMENTATION
Approval scope: C# service, APIs, producer adapters, case lifecycle observation,
live Dataverse read model and controlled cutover.
Dependencies: Stage 2 schema and contracts.

3.1 Public service surface

Yes: a Dataverse plug-in can back callable Dataverse Custom APIs. It is not a
free-standing web server. Dataverse supplies authenticated invocation and
solution deployment; the plug-in supplies validation and business projection.

Proposed unbound/global Custom API Actions:
- rfd_RecordEmailProcessEvent: receive/register a process and append an allowed
  event, updating its stage/process projections in one Dataverse transaction.
- rfd_LinkEmailProcessCase: validate and add the unique process/case relationship;
  record provenance and reconcile current case state to cover link/close races.
- rfd_RecordCaseLifecycle: internal/authorized lifecycle reconciliation contract,
  not a command that closes cases. Reconcile linked processes from actual case
  transitions; reject arbitrary caller claims that a case has been resolved.
- rfd_GetEmailProcessState: scoped current process + stage executions/case links.
- rfd_GetEmailProcessEvents: bounded ordered event history with continuation.
- rfd_ListEmailProcesses: scoped filters, paging and consistent summary counts.

Prefer Actions (IsFunction=false) even for read-only operations so Power Automate
and the Code App share one contract. Power Automate's Dataverse connector does
not execute Functions. Use typed primitive input/output properties; a JSON
envelope is a schema-versioned String with validation, not a fictitious native
arbitrary-object parameter type. Limit envelope length, page size and fan-out.

Illustrative event request (proposed field names):
  SchemaVersion=1, EventId=<stable GUID>, ProcessId=<GUID or null at intake>,
  StageExecutionId=<stable GUID>, StageCode=classify, Attempt=1,
  SourceExecutionId=<real flow run>, EventType=completed,
  OccurredAtUtc=<captured time>, Outcome=succeeded, CaseId=<optional GUID>.
Receipt returns ProcessId, EventId, Applied/AlreadyRecorded and Revision.
The writer derives source hashes, actor identity and recorded time server-side.
It validates source-specific payloads; parameters are never authority by themselves.

3.2 Implementation and security

- C# IPlugin, sandbox, currently documented .NET Framework 4.8 target for new
  projects; verify current SDK/toolchain at implementation. Do not use .NET 8
  assemblies or ILMerge for Dataverse plug-in registration.
- Use supported PAC/Visual Studio/Plug-in Registration tooling. Custom API
  PluginTypeId supplies MainOperation; package API definitions, parameters,
  responses, assembly/package and observer/guard steps in the solution.
- The source will add a server project and unit/integration tests plus generated
  solution artifacts. Packaging/export details are approved at Stage 3, not
  hand-authored solution XML or a custom deployment bypass.
- IsPrivate=false for documented discovery/code generation; it is not a security
  boundary. Use an appropriate EXISTING ExecutePrivilegeName and explicit
  producer/record authorization. Do not invent an unsupported custom privilege.
- AllowedCustomProcessingStepType=None for the narrow API contract unless a
  reviewed extension is required. Event/table mutation guards are separate steps.
- Execute reads in the authenticated caller's context and reauthorize each
  page. Do not accept an arbitrary caller/user ID or query as an administrator.
- Writers need the requisite narrow table privileges. Restrict event/projection
  direct CRUD through server-side guards recognizing the trusted API execution
  context, not a caller-set flag; validate command scope and initiating identity.
  Test all cumulative role grants and bypass attempts. Do not simply use SYSTEM
  to sidestep authorization. Definition/retention administration is separate.
- Only authorized workflow/tool identities can assert corresponding business
  outcomes. The browser may register its own approved demo operations, not
  fabricate a bank-agent action or resolve a case through telemetry.

3.3 Transactions, concurrency and idempotency

- Persist event and stage/process projection atomically inside the synchronous
  API operation on standard tables, using IOrganizationService. Verify actual
  IsInTransaction behaviour in integration tests; no same-environment HTTP calls
  or nested ExecuteTransaction/ExecuteMultiple inside plug-ins.
- Read the Process row version, apply a validated reducer, and use explicit
  IfRowVersionMatches updates. Table configuration alone does not prevent the
  plug-in default of AlwaysOverwrite.
- Increment a per-process projection revision and assign it to the new event.
  Parallel writers retry complete requests after a concurrency fault, outside
  the failed transaction. No global counter/hot row across unrelated processes.
- Same stable EventId/source key and same canonical payload -> AlreadyRecorded.
  Same identity with different facts -> conflict requiring investigation.
- Allocate retry identities once before the connector retry boundary. New
  business attempts receive new executions; transport retries keep their IDs.
- Never catch a Dataverse data fault and keep writing/querying in that aborted
  transaction. The caller retries through a fresh request with bounded backoff.
- Reducer rules reject stale regression: late started cannot undo completed;
  old case versions cannot undo a newer reopen/resolve; parallel branches and
  partial coverage are represented explicitly.
- This is telemetry idempotency, NOT exactly-once email sending, agent execution
  or financial servicing. Do not retry the business operation to repair logging.
- If a business operation succeeds but telemetry fails, keep handling fail-open,
  expose the gap and reconcile. This is not a lossless regulated audit/outbox for
  the underlying banking transaction.

3.4 Case Management Workflow and independent case observer

Case Management Workflow must be able to report progress, but it should not be
the only place capable of detecting a case closed through another app/API.

Recommended default: an asynchronous PostOperation incident Update observer
with filtered statecode/statuscode and minimal pre/post images. Compare actual
old/new values; filtering attributes alone only mean a field was included.
The observer records committed lifecycle facts; the case-management workflow
records its distinct attempted actions, agent calls, success/failure and links.
Both call the shared writer/reducer rather than independently patching status.

- Inventory the intended custom flow before editing. Do not enable or modify
  the inactive Microsoft agent flow merely because its name sounds relevant.
- Observe the actual result of supported case resolution (CloseIncident),
  cancellation, merge and reopening. CloseIncident is not a catch-all event
  for every lifecycle change, and it does not support the same entity images
  as Update. Prove actual message registrations in this tenant.
- Capture the case source version and pre/post states from the change context
  rather than treating a later current-state read as historical truth. Validate
  version availability during the spike; if unavailable, label current-state
  reconciliation honestly or separately approve durable transition capture.
- Deduplicate the same committed case transition by stable source identity:
  case + captured version/transition + event type, expanded per linked process.
  Never deduplicate forever on case ID plus "closed": close/reopen/close must
  produce three distinct lifecycle events.
- Reconcile all explicit process/case links, not the most recent email from
  that customer. Update only applicable blocking links/stage executions.
- A resolved case completes a process only if the remaining required branches
  and blocking cases are satisfied. Cancellation/merge are not labelled success.
- On reopen, create a new review execution/lifecycle cycle and preserve the
  previous completion history. Late deliveries of older closure events must
  not reverse the newer state.
- Bound plug-in work. Large link fan-out uses paged, idempotent follow-up work
  through the case workflow/async worker, with incomplete reconciliation visible.
- No case update from the telemetry observer; avoid recursion and feedback loops.

Default reliability policy: case closure must not fail because the UI ledger
is unavailable. Async failures use native job monitoring/retry and reconciliation.
If lossless same-transaction case capture is later required, a synchronous
observer/durable receipt is a SEPARATE decision: its failure may roll back the
case change. Do not claim both fail-open business writes and lossless capture.

3.5 Reads and app integration

Use generated Dataverse API services (installed SDK meets the documented
1.1.1+ prerequisite); confirm CLI discovery and actual generated signatures.
No embedded credentials, replacement Graph gateway or elevated read proxy.

- List filtered Process projections with selected columns and paging; fetch
  execution/event details only for the selected process.
- Return actual process, stage, record references, source/coverage, revision
  and optional event-page cursor. Read actions do not mutate process state.
- Order timeline by process revision/event ID with an explicit upper revision
  for a bounded page session. Late-recorded events retain original occurred time.
- Refresh around 10 seconds initially, non-overlapping and visibility-aware.
  Use row/revision-aware merging and modified-time paging with overlap; do not
  skip records sharing a timestamp or let an old response replace a newer one.
- UI health distinguishes unknown, stale, partial and replayed history. Timeline
  can be reconstructed within retained event coverage; snapshots are projections.

Acceptance:
- Concurrent duplicate intake creates one process; retries do not inflate events.
- Two emails in one conversation remain two processes; repeat customer subjects
  and Reply-To values never become correlation keys.
- One-case/many-process and many-case/one-process closure/reopen work correctly.
- Actual closed/cancelled/merged outcomes from workflow and model-driven UI are
  reflected; duplicate triggers and old events do not regress projections.
- Invalid event transitions, wrong producer, unrelated case IDs and direct
  event modifications are denied; other users' process/event pages stay private.
- Tool output, not agent prose, establishes business-action success.
- Demonstrate API round trip from app and flow, then end-to-end Help intake ->
  classifier -> handler/tool -> case -> human review/closure in a controlled pilot.
- Demonstrate telemetry failure without automatic business-operation retry and
  explicit reconciliation of the missing observation.
- Target foreground UI visibility within one normal polling interval plus read
  latency after the ledger commit. This is a measured pilot target, not an SLA.

Rollback: disable producer adapters/observer registrations and select the old
read mode. Preserve ledger records, solution backups and business records.
Do not remove user-edited workflow changes or erase event history automatically.


STAGE 4 - REAL-TIME EVENT BUS AND BROWSER UPDATES
Approval scope: separately budgeted Azure integration, security review and
published-host feasibility proof. Optional; Stages 1-3 work without Azure.
Dependencies: reliable Stage 3 ledger and query API.

4.1 Recommended architecture

  Workflow / agent host / case observer
                 |
                 v
  Dataverse Custom API
       [event + projection + notification outbox, one ledger transaction]
                 |
                 v
  Azure outbox dispatcher -> Service Bus topic -> notification subscription
                                                    |
                                                    v
                                              Azure Function
                                                    |
                                                    v
                                              Azure Web PubSub
                                                    |
                                      authorized refresh hint
                                                    v
                           Code App -> caller-secured Dataverse query API

Add rfd_processnotification with DeliveryId, ProcessId, EventId, Revision,
notification schema version, publication state, lease/attempt/next-attempt
metadata and sanitized last error. Create it in the SAME transaction as the
ledger event/projection when the feature is enabled. Dispatch bookkeeping does
not mutate the immutable business event.

This guarantees notification intent for a committed LEDGER update, not for an
external bank operation or async case update that failed to reach the ledger.

The dispatcher reads committed pending rows in bounded batches, leases with
concurrency control, publishes a minimal allowlisted payload, and marks success
only after Service Bus accepts it. Use one durable subscription for the
notification workload, not a broker subscription per browser.

4.2 Security and feasibility gate - do this before the full bus rollout

Current Code Apps documentation specifies default CSP connect-src 'none'.
External WebSockets require an explicit environment-level policy allowance;
localhost success does not establish published-player compatibility.

Proposed negotiation route: Entra-authenticated backend exposed by a narrow
Power Platform custom connector and generated Code App service. Validate the
actual per-user connection identity; do not trust a supplied user ID or assume
the Power Apps host exposes its access token.

The backend issues a short-lived Web PubSub client URL for server-authorized
groups. It must check membership against the permitted process/operations
audience and Dataverse access, not an arbitrary requested group name. Grant
neither client group-publish nor arbitrary self-join rights. Row/group access
does not automatically inherit from Dataverse. Even a process GUID is metadata
that an unauthorized user should not learn.

Allow only the required wss:// host in Code App CSP. Do not replace policies with
wildcards or weaken other apps in the environment. Approve any HTTPS/CORS and
WebSocket origin settings separately; CORS is not WebSocket authorization.
Do not store access URLs, reconnect tokens, SAS or connection strings in source,
logs or persistent browser storage. The short-lived browser client token is
not a broker/admin credential. Permission revocation requires active group
removal/disconnection or reauthorization; token expiry alone may not close a
long-lived connection.

Stage 4A go/no-go:
- A minimal published Code App negotiates and receives an authorized test hint.
- CSP, player embedding, corporate proxy and reconnect/logout work.
- A second user cannot subscribe to an unauthorized process/group.
- No host-token extraction, browser secret or elevated CRM read is required.
- Confirm subscription/region, owners, licensing, budget and CSP approver.
If this cannot be proven with approved controls, stop and retain polling.
Stage 4 approval can be limited to this spike before authorizing Stage 4B rollout.

4.3 Event semantics and resilience

Notification payload: schema version, opaque EventId, authorized ProcessId and
Revision. Exclude subjects, email addresses, names, bodies, prompts, case
descriptions, attachments, balances and unrestricted execution contexts.
If per-process audience authorization is unavailable, use only an explicitly
approved coarse refresh hint with no record identifiers.

- Service Bus and relay delivery are at least once. Use stable MessageId and
  idempotent processing; duplicate detection has a bounded window, not an
  exactly-once guarantee. A crash after publish but before acknowledgement
  can legitimately cause redelivery.
- For UI refresh hints, order-independent revision handling is simpler than
  mandatory broker sessions. Consumers ignore old revisions and coalesce bursts.
  If another business consumer needs ordered work, give it a separate contract
  and per-process sessions with correctly ordered production.
- The browser does not apply arbitrary event payloads as business truth. It
  invalidates the affected process and reads authorized state from Dataverse.
- Complete broker messages after the relay hand-off succeeds; Web PubSub
  acceptance is not proof every browser displayed it. Reconnect/foreground
  always fetches current state. Long outages reconcile from the ledger.
- Maintain periodic safety reconciliation and automatic ~10-second polling
  fallback when push disconnects; show Live/Reconnecting/Polling/Stale status.
  Do not increase 10-second cached stale data just because a notification arrived:
  affected-process refresh bypasses/invalidates the relevant cache.
- Alert on outbox age/failures, worker lag, DLQ count/age and socket failures.
  Replay is explicit and audited. Broker DLQ data needs its own retention cleanup.
- Azure outages must not stop email processing or case closure. Outbox intent
  waits safely; backlogs are bounded/visible and recoverable.
- Future external producers use authenticated adapters into the same API.
  Publishing to a bus does not authorize a business outcome. Keep inbound
  commands separate from outbound notifications to prevent feedback loops.

4.4 Alternatives and cost decision

Native Dataverse asynchronous Service Bus service endpoints are supported and
can publish to a topic, but serialize RemoteExecutionContext, potentially
including input/parent context and entity images. Filtering attributes is not
payload redaction; native system jobs/retries do not provide an application
replay ledger. Prefer the explicit outbox dispatcher for controlled egress and
identifiers. Native publication is an alternative only after payload review.

Webhooks are not a durable browser bus and can couple response time/failure to
the caller. Event Grid is useful for broader Azure integrations but adds no
direct Code App browser subscription by itself; do not assume native general
Dataverse row-to-Event-Grid support. Application Insights is diagnostics, not the
near-real-time business ledger. No documented Power-Platform-only push stream
for this Code App browser scenario was established in the research.

Budget for Service Bus Standard or higher for topics, Web PubSub connections/
messages, Function compute/storage/monitoring, Dataverse capacity/request limits
and connector/app licensing. Use current Azure SDKs, not retired Service Bus
libraries from old samples. No fixed monetary estimate without regional and
volume inputs.

A two-second server outbox poll is about 43,200 idle reads/day before paging.
For the demo, enable fast dispatch only for scheduled demo windows or an
approved active-viewer lease, and back off when idle. Measure load and respect
Retry-After. If continuous sub-five-second operation is required, explicitly
budget the always-on dispatcher and warm worker capacity; do not hide that cost.

Stage 4B acceptance:
- Proposed warm/foreground target: p95 <= 5 seconds, p99 <= 10 seconds from
  successful ledger commit to completed UI refresh. Measure at least 100 pilot
  changes under stated load; report cold starts and failures separately.
- Restart dispatcher after publish-before-mark and worker after relay-before-ack:
  duplicate hints cause no duplicate business events or incorrect UI.
- Simulate out-of-order hints, extended disconnect, access revocation, Azure
  outage and DLQ replay; the UI converges to Dataverse state.
- Demonstrate case closure/reopen from another client updating the authorized
  process view without waiting for the normal full-snapshot poll.
- Agree ongoing cost/retention owner and an operational recovery runbook.

Rollback: disable notification dispatch/client push and restore polling.
Do not delete the durable ledger. Drain or retain the outbox/DLQ under the
approved retention policy; remove CSP exceptions only after other consumers
of the environment policy have been checked.
