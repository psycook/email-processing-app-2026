REMAINING RELEASE GATES

1. Schema inspection, Active keys, seed publication and export/unpack are complete.
   Reinspect before activation if metadata or the canonical contract changes.
2. Approve operational ownership, narrow producer/reader roles and field-security
   access. The default server policy intentionally authorizes nobody.
3. Configure identities, observer step IDs, local signing/cursor material and
   register the dependent-assembly plug-in package and guard steps before exposing
   writers. Runtime API configuration is documented in server/runtime-prerequisites.txt.
4. Prove actual Dataverse transaction rollback, concurrency, duplicate intake,
   image availability and two-user visibility. Unit tests cannot establish these.
5. The actual customer/case logic has been located in the Card Servicing agent's
   query-or-update-card InlineAgentSkill and generic Dataverse MCP InvokeMCP
   binding. These are not deterministic workflow actions. The inspected
   InvokeAgent configuration exposes agentId/prompt, with no verified typed
   process-context input or per-tool interception hook. The approved Stage 3
   route is deterministic flow orchestration: move customer lookup, case mutation
   and process linkage into reviewed flow/tool actions that call the plug-in APIs,
   with the agent reduced to recommendation-only output. No Contact is inferred
   from email headers and the opaque host event alone cannot safely associate a
   Case. The automatic saved-agent/MCP patch remains refused.
6. Identify the intended custom Case Management Workflow or create an approved
   owned deterministic orchestration. Do not activate or edit
   the inactive Microsoft-managed case-management agent flow by name.
7. Review current Help source/ETag, API binding and node/producer policy, then
   explicitly approve live cutover. Pilot fault/skip/termination behaviour in
   native Power Automate before calling the candidate production-safe.
8. Only after those gates, publish the new app. Pilot emails require exact
   message previews and approval. Do not claim end-to-end tracking before a real
   authorized email -> agent/tool -> case -> closure/reopen run is observed.

KNOWN BOUNDED LIMITS

- No outbox, Azure bus, browser WebSocket, CSP or Stage 4 resource changes.
- Ingress-first identity; exact app-draft-to-intake correlation remains unproven.
- Case observer fan-out is bounded; larger sets need a paged reconciliation
  worker. Reconciliation markers are not automatically cleared.
- No production retention/deletion or full database rebuild tool.
- Generated read metadata is contract-derived until verified against registered
  live API signatures. Missing APIs fail visibly, never return synthetic results.
- Build currently reports a large process-renderer bundle warning; it still
  type-checks and builds. A scoped code-split can be added before release.
